# 汎用AI開発リポジトリ構造 設計ガイド(テンプレート)

> **このファイルは何?** どんなプロジェクトにも使える「AIと一緒に開発するためのリポジトリ構造」の設計ガイドです。
> 特定のプロジェクトに依存しません(=テンプレート)。初学者でも読めるよう用語から説明します。
> **まず「0. 3分で全体像」だけ読めばOK**。要件の出典は同階層の `REQUIREMENTS.md`。
>
> 設計は、公開フレームワーク調査 + 複数AIによる**敵対的監査(まず却下を試すレビュー)**を経て確定したものです。

---

## 0. 3分で全体像

このテンプレートは **3つの制約**を同時に満たすためにあります。

1. **完全 in-repo(プロジェクト内で完結)** — `~/.claude` 等プロジェクトの外に知識・設定を置かない。リポジトリを渡すだけで同じ挙動。
2. **ベンダー中立** — Claude Code だけに密結合しない。Codex / GitHub Copilot / Cursor などでも同じ正本を使える。
3. **段階的な自己改善** — AIが目標に向けて試し、評価(eval)が良くなった時だけ採用する。最終的に人手なしの自動化を目指すが、安全のため**半自動から始める**(★)。

### 置き場所マップ(結論)— 「誰が編集してよいか」で分ける

```
種類                          置き場所            編集してよいのは
──────────────────────────────────────────────────────────────────
正本(AIへの最重要指示)     → AGENTS.md          人間(各ツールはここを読む)
不変の目標・規範・評価の核   → governance/        人間が一度だけ凍結(AI編集禁止)
AIが日常使う評価(可視基準)  → eval/              AI可
AIが育てる知識・進捗・判断   → knowledge/         AI可(追記式)
試行の履歴(機械生成)       → provenance/        自動
実装そのもの                 → src/(等)          AI可
個人メモ(共有しない)       → *.local.*          各自(gitignore・ループ対象外)
```

### ★ 一番大事な但し書き(正直に)

「**人間が統治せず、AIが完全自動で自己改善**」を安全に回すには、改善の“審判”である **eval が信頼でき・ごまかせない**必要があります。
多くのプロジェクトでは最初その前提が整いません(評価が甘い/AIが評価自体を抜け道にできる/独立した検証が無い)。そこで本テンプレートは:

> **完全自動(auto)は既定OFF。まず半自動(semi-auto=人間が改善を承認)。
> 「信頼できる独立評価(holdout)を封印できた時」に、同じ機構を無改造で auto へ昇格する。**

= 「evalゲート自動承認」という目標を**捨てず、前提が整うまで安全に延期**する設計です(→ 第7章)。

## 1. 3つの制約(なぜこの設計か)

| 制約 | 解決したい問題 | この設計での解決 |
|---|---|---|
| ① in-repo完結 | 知識が個人領域(`~/.claude`)にあると、渡しても再現しない | すべてリポジトリ内のファイルへ。ツール固有の外部依存を持たない |
| ② ベンダー中立 | 特定AIツール専用機能に依存するとロックインする | 正本=`AGENTS.md`、各ツールは**参照1行**のアダプタ |
| ③ 段階的自己改善 | 人手で設計を更新し続けるのは続かない | eval(審判)を門番にし、改善時だけ反映。前提が整えば無人化 |

## 2. 用語ミニ辞典(初学者向け)

| 用語 | かんたんな意味 |
|---|---|
| **AGENTS.md** | 複数のAIツールが共通で読む「指示の正本」。ベンダー中立の標準ファイル |
| **アダプタ** | 各ツール固有の入口ファイル。中身はコピーせず「正本を読め」と1行だけ書く |
| **governance/** | 目標・規範・評価のしくみを置く保護区画。**人間が一度だけ決め、AIは触らない** |
| **eval(評価)** | AIの変更が良くなったかを判定するしくみ(=自己改善の“審判”)。中身はプロジェクト次第 |
| **可視基準 / holdout** | AIが最適化に使う評価(可視)/ AIに見せず最適化もさせない独立評価(封印)。過学習・ごまかし検知用 |
| **canary(カナリア)** | 封印データが学習・生成に漏れていないか見張る“目印”。混入したら自動失格 |
| **provenance(由来)** | 「いつ・何を変えて・評価がどう動いたか」の履歴台帳 |
| **ADR / DECISIONS** | 「なぜその設計にしたか」の記録(Architecture Decision Record) |
| **SSOT** | Single Source of Truth = 1つの事実は1か所だけに書く原則 |
| **hermetic(自己完結)** | リポジトリの中だけで完結し外部に依存しないこと |
| **semi-auto / auto** | 半自動(人間が承認)/ 完全自動(evalだけで承認)。本設計は semi-auto から |
| **reward hacking** | AIが“評価値だけ”上げる抜け道(評価を書き換える等)。最大の敵 |
| **context collapse** | 知識ファイルを全書換して情報が激減する事故。だから**追記式**にする |

```

        │ governance/(人間が一度だけ凍結・AI編集禁止) │
        │   GOAL(目標) / CONSTITUTION(規範) /         │
        │   eval評価核 / holdout(封印した独立評価)    │
        └───────────────┬─────────────────────────────┘
                        │ 審判として参照(改変は機械で拒否)
                        ▼
 AI ──変更──▶ eval(可視基準で採点) ──良くなった?──▶ Yes→採用(commit)
 (src/ と                                          └─ No →破棄(rollback)
  knowledge/だけ                  ▲                       │
  書込可)                        │                       ▼
        ▲                        └── holdoutは“予算制”で  provenance/ に1行記録
```

### feel-flow から取り込んだ構造(どこに効いているか)

| feel-flow の要素 | 本テンプレートでの反映先 |
|---|---|
| MASTER.md(中央ハブ・最初に読む) | `AGENTS.md`(正本=ハブ。docs/ へ目的別ナビ) |
| 番号付きフォルダ 01-context〜06-reference | `docs/`(人間が読む「仕様」層) |
| DECISIONS.md(ADR) / GLOSSARY.md | `docs/06-reference/` |
| 1行要約の索引・目的別ナビ | AGENTS.md のナビ書式 `- [パス](パス) - 動詞+対象+(スコープ)` |
| 最小起点 + 段階拡張 | `docs/01-02` は最小、`03〜06` は ◇ トリガー拡張 |
| 配布境界(配布物 vs 運用物) | 普遍層=テンプレ配布(第6章) / governance・knowledge=リポ運用 |

> **`governance/` と `docs/` の違い(重要)**:`governance/`=**機械が強制する“契約”(凍結・AI編集禁止)**、
> `docs/`=**人間が読む“仕様・理由”(spec, feel-flow流)**。両者はリンクで繋ぎ内容は重複させない(SSOT)。
> 例:`governance/GOAL.md`=測れる達成条件 / `docs/01-context/PROJECT.md`=背景・要件の物語。

## 5. 4つの置き場所と「編集してよいのは誰か」

人間のレビューが無い前提では、保護を“場所(編集主体)”で機械的に表現するのが肝です。

| 置き場所 | 役割 | 編集主体 | 保護のしかた |
|---|---|---|---|
| `governance/` | 目標・規範・評価核・holdout・門番 | **人間が一度だけ凍結** | AGENTS.md宣言 + pre-commit + 門番のハッシュ照合 |
| `eval/` | AIが日常使う可視評価 | AI可 | governance/eval を呼ぶだけ(核は触れない) |
| `knowledge/` | 進捗・判断・設計哲学・教訓 | AI可(**追記式**) | 全書換禁止(STATE.md のみ全書換可) |
| `provenance/` | 試行の履歴 | 自動生成 | 機械再計算(手入力しない) |
| `docs/` | 人間が読む仕様・設計・理由(spec層)【feel-flow】 | 人間中心(AIも読む) | 番号フォルダで責務分離。AGENTS.md がナビ |

## 6. 設計思想の「3層」(普遍 / プロジェクト固有 / 個人)

要件の中心である3層分離は、上の構造の中で**こう対応**します(専用ディレクトリは作らず、置き場所とタグで表現)。

| 層 | 意味 | 物理的な置き場所 |
|---|---|---|
| **普遍(プロジェクト非依存)** | どのプロジェクトでも効く流儀 | `AGENTS.md` のクリティカル核 + `governance/CONSTITUTION.md` の【普遍原則】 |
| **プロジェクト固有** | このプロジェクト固有の目標・設計 | `governance/GOAL.md` + CONSTITUTION の【固有原則】 + `docs/`(仕様) + `eval/` + `knowledge/` |
| **個人** | その人だけの好み | `*.local.*`(gitignore・ループ対象外) |

### 「普遍」と「in-repo完結」をどう両立するか(重要)

「普遍(どのリポでも共通)」と「in-repo(外部参照しない)」は一見矛盾します。解決策:

> **普遍層はテンプレートとして一元管理し、各リポへは“コピー”して持たせる**(実行時に外部を参照しない)。
> 同期はテンプレートからの**再生成/再コピー**で行う(=runtime依存ゼロのまま、普遍層を再利用)。

- 各リポは普遍層の**自分用コピー**を commit して持つ(in-repo)。
- 普遍層を更新したら、テンプレート → 各リポへ再コピー(symlinkは使わない: 環境依存・脆弱)。

## 7. 自己改善ループ(2モード)

`governance/MODE.md` で切替。**昇格(semi-auto→auto)は人間がADRを書いて一度だけ**行います。

### モードA: semi-auto(既定・最初はこれ)
```
[1] AIが GOAL / CONSTITUTION / STATE を読み、src/ か knowledge/ に「1つ」変更案を作る
[2] eval/run_local.* で可視評価を測る(変更前→後)
[3] AIが「何を・なぜ・次どうするか」を1段落で説明
[4] 人間が “可視評価が改善 ∧ 既存テスト緑 ∧ 規約違反なし” を確認して commit
    holdout(独立評価)は開けない(温存)
```

### モードB: auto(完全自動。holdout昇格ゲートを通った後だけ起動)
被験AIとは**別プロセスのドライバ**が、git worktree 上で1サイクル回す。AIの書込は `src/` と `knowledge/` に**物理限定**。

```
[前] ドライバが governance/** と評価核と input_manifest のハッシュを記録
[1] AIが1変更(範囲外への書込はドライバが破棄)
[2] worktree外の固定された評価で可視評価を測定(前→後)
[3] 自己申告でなく「終了コード+結果ハッシュ」だけを信頼
[4] 教訓を PLAYBOOK に“追記”(全書換禁止)
[5] ハードゲート(全部ANDで満たす時だけ採用):
     ・governance/**・評価核・しきい値・入力manifest のハッシュ不変
     ・門番ファイルに差分なし ・canary 不在(漏洩検知)
     ・規約の[機械検証]項目パス ∧ 既存テスト緑
   ソフトゲート: 可視評価が「最小検出差(複数試行の中央値)」を超える有意改善
[6] 採用→ドライバがcommit(--no-verify禁止) / 不採用→worktree破棄(=自動rollback)
[7] provenance/eval-log.jsonl に1行記録(採否どちらも)
[8] holdout は毎回使わない:
     ・連続採用N回ごとに「開封予算1」を使って1回だけ独立評価
     ・可視↔独立の差が開き続ける / 独立評価が悪化傾向 → ループ自動停止(人手で再封印)
     ・開封予算が尽きる / 一定回数 採用ゼロ → 自動停止
```

**なぜこの形か**:独立評価を毎回の合否に使うと“まぐれ当たり”を選び続けて本当の質が劣化します(多重比較の罠)。
だから**日常の合否は可視評価、holdoutは予算制の“抜き取り監査”**にし、悪化傾向なら止めるだけにします。

### eval(審判)はプロジェクトごとに中身が違う(汎用化のポイント)

| プロジェクト種別 | 可視評価(eval)の例 | 独立評価(holdout)の例 |
|---|---|---|
| ソフトウェア一般 | テスト/型/lint/ベンチマーク | リリース前の受け入れテスト(AIに最適化させない) |
| 機械学習 | 検証メトリクス | 別出典・本番分布の封印データ |
| 文章/ドキュメント | rubric採点 / リンク・整合検査 | 第三者レビュー基準・別サンプル |

**共通原則**:eval は「機械が客観判定でき・AIが書き換えられない」物にして `governance/` に置く。それが無い段階では semi-auto に留める。

## 8. ガードレール(失敗モード → 対策)

自己改善ループは放置すると壊れます。主要な失敗モードと対策:

| 失敗モード | 何が起きる | 対策 |
|---|---|---|
| **独立評価のゲート退化** | holdoutを毎回judgeに使い、まぐれ選抜で本当の質が劣化 | holdoutはゲートから外し**予算制の抜き取り監査**に。日常は可視評価 |
| **門番の乗っ取り(reward hacking)** | AIが評価核/しきい値/hookを書換えて“通す” | 門番を `governance/` に隔離+**別プロセスのドライバがハッシュ照合**+commitはドライバ経由(`--no-verify`禁止) |
| **独立評価の代表性ゼロ** | 可視と同じ分布の評価では汎化を測れず審判が空洞 | **信頼できる独立holdout封印を auto昇格の前提条件**に。それまで semi-auto |
| **context collapse** | 知識ファイル全書換で情報激減 | knowledge は**追記式**。廃止は印→古い行は物理削除しgit履歴へ(activeのみ残す) |
| **Goodhart(評価過学習)** | 可視評価は上がるが本質は劣化 | 単一指標禁止(複数基準を同時)+ 独立評価の非悪化監視 |
| **ドリフト** | 固定評価に最適化し現実とズレ続ける | 評価入力を版管理。可視↔独立の差の拡大で自動停止。前提が崩れたら達成判定保留 |
| **肥大化** | 台帳が無限増殖 | 初期は履歴1本のみ。剪定はサイクル末に決定論ルールで(外部依存ゼロ) |

> **原理的な限界(正直に)**:“絶対にハックされない eval” は存在しません。だから唯一の人手点=
> 「**GOAL + CONSTITUTION + 独立holdout を一度だけ凍結**」と「独立評価が悪化した時の再封印」は残します。それ以外を無人化します。

## 9. ベンダー中立アダプタ(各ツールの読ませ方)

正本は `AGENTS.md` の**1つだけ**。各ツールの入口は「参照1行+クリティカル核の同一文言」で、**本文を複製しません**(SSOT)。
クリティカル核は1ソースから生成し、pre-commit でハッシュ一致を検証(各ツールの“到達の深さ”のばらつきを封じる)。symlinkは使いません(環境依存・脆弱)。

| ツール | ネイティブに読む物 | 実装 | 撤退コスト |
|---|---|---|---|
| **Codex** | `AGENTS.md`(直下) | アダプタ不要 | 0 |
| **Cursor** | `AGENTS.md` / `.cursor/rules` | `.cursor/rules/00-defer-to-agents.mdc`(委譲) | 1ファイル |
| **GitHub Copilot** | `.github/copilot-instructions.md` | 「正本=AGENTS.md」+核 | 1ファイル |
| **Claude Code** | `CLAUDE.md` | 「正本=./AGENTS.md」+核(`@import`は使わず素の参照文) | 1行〜1ファイル |
| **Gemini / Cline 他** | `GEMINI.md` / `.clinerules/` 等 | 使い始めたら同形で追加 | 1ファイル |

> ⚠️ **要確認**:各ツールが「実際に何を読むか」と「AGENTS.md の標準化状況」は時期で変わります。導入前に各ツール最新docで確認。
